# Laravel + Inertia + Vue Audio/Video Schedule Generator

## Role

You are a Senior/Lead Laravel Developer and experienced Vue.js developer.

Build a lightweight web application for a local Jehovah's Witness congregation that generates a monthly **Audio/Video support schedule**.

The application will replace an existing Google Apps Script workflow with a clean Laravel application while keeping congregation data in **Google Sheets**.

## Data persistence decision

Google Sheets is the chosen persistence layer because:

- The existing workflow already uses Google Sheets
- All domain data is tabular (settings, brothers, meetings, schedule rows) and maps cleanly to sheet tabs
- The repository abstraction already isolates storage from scheduling logic
- Render's ephemeral filesystem is no longer a concern — data lives in Google Drive
- Congregation coordinators can inspect or edit data directly in the spreadsheet if needed

Constraints to respect:

- Brother IDs must be generated by the application (Sheets has no auto-increment)
- `busy_brothers` is stored as comma-separated IDs in one cell
- Use a service account with Editor access; credentials must not be committed
- Tests must use a fake storage implementation, not the live API
- Google Sheets API quotas apply (~300 read/write requests per minute per project — sufficient for this app)

The application must be:

- Dockerized for local development
- Built with Laravel + Inertia.js + Vue 3
- Styled with Tailwind CSS
- Database-free (no SQL database)
- Persistent using **Google Sheets** through a repository abstraction
- Testable
- Deployable to Render
- Structured so the persistence layer can later be changed to SQLite or another storage system without rewriting the scheduling logic

# 7. Storage Architecture

The application must be database-free (no MySQL, PostgreSQL, or SQLite).

Persist all application data in a **single Google Spreadsheet** using the Google Sheets API.

The spreadsheet replaces the JSON files used in earlier designs and aligns with the congregation's existing Google Sheets workflow.

Create one spreadsheet with four tabs:

```text
Settings
Brothers
Meetings
Schedule
```

Do NOT access the Google Sheets API directly from controllers.

Create:

```text
app/Services/GoogleSheetsService.php
```

and repositories:

```text
app/Repositories/
├── SettingsRepository.php
├── BrotherRepository.php
├── MeetingRepository.php
└── ScheduleRepository.php
```

Controllers interact with repositories.

Repositories interact with `GoogleSheetsService`.

Define a narrow interface (e.g. `SpreadsheetStorageInterface`) so repositories depend on an abstraction, not the concrete Google client. This keeps tests mockable and allows a future swap to another backend.

# 8. GoogleSheetsService

Use the official Google API PHP client:

```bash
composer require google/apiclient
```

Authenticate with a **Google Cloud service account**. The service account must have edit access to the target spreadsheet.

Required environment variables:

```env
GOOGLE_SHEETS_SPREADSHEET_ID=
GOOGLE_SERVICE_ACCOUNT_JSON=
```

`GOOGLE_SERVICE_ACCOUNT_JSON` should contain the full service account key JSON (as a single env var string on Render, or as a mounted file path in local Docker).

The service should provide functionality such as:

```php
readSheet(string $sheetName): array
writeSheet(string $sheetName, array $rows): void
readSettings(): array
writeSettings(array $settings): void
```

Requirements:

- read and write each tab as structured row data
- map sheet rows to the same domain shapes used by repositories (settings object, brother records, meeting records, schedule records)
- validate data before writing
- handle API errors gracefully with clear application-level messages
- cache reads briefly where appropriate to reduce API quota usage (optional, configurable)
- never expose credentials or spreadsheet IDs in client-side code
- use batch update operations where practical to minimize API calls

### Sheet layouts

**Settings** — single data row (row 2; row 1 is headers):

| congregation | address | title | include_preparation |
|---|---|---|---|

**Brothers** — one row per brother:

| id | name | is_ms | can_audio | can_video | can_mic | can_stage | can_prep | training_role |

**Meetings** — one row per meeting:

| date | skip | allow_trainee | busy_brothers |

Store `busy_brothers` as a comma-separated list of brother IDs (e.g. `2,5`).

**Schedule** — one row per generated assignment:

| date | audio | video | mics | stage | preparation |

Store brother IDs in assignment columns. Use empty cells for `null` assignments.

### ID generation

Google Sheets does not auto-generate brother IDs. The `BrotherRepository` must assign the next available integer ID when creating a brother (max existing ID + 1).

### Setup command

Provide an Artisan command to initialize the spreadsheet headers and default settings row if the tabs are empty:

```bash
php artisan sheets:setup
```

Document how to create the Google Cloud project, enable the Sheets API, create a service account, share the spreadsheet with the service account email, and configure environment variables.

# 16. Scheduling Pipeline

The algorithm should follow this general order:

```text
1. Filter meetings
2. Sort meetings
3. Determine meeting type
4. Build scheduling state
5. Determine eligible candidates
6. Apply qualification rules
7. Apply busy restrictions
8. Apply trainee restrictions
9. Apply cooldown
10. Apply MS requirement
11. Apply weekend swap preference
12. Apply fairness
13. Assign roles
14. Assign preparation
15. Validate generated schedule
16. Return schedule + warnings
```

# 18. Audio/Video Cooldown

A brother assigned to Audio or Video during:

```text
Week N
```

```text

```

```text

```

Cooldown applies to:

- Audio
- Video

Cooldown does not automatically apply to:

- Mic
- Stage
- Preparation

# 23. Midweek-to-Weekend Swap

When a midweek and weekend meeting occur in the same week, attempt to swap Audio/Video roles.

Example:

Midweek:

```text
Audio = Audio Trainer
Video = Video Trainer
```

Weekend:

```text
Audio = Video Trainer
Video = Audio Trainer
```

For trainees:

```text
Audio Trainee → Weekend Video
Video Trainee → Weekend Audio
```

only if the brother is qualified for the swapped role.

The swap is a preference/rule, not a reason to create an invalid assignment.

If swapping violates:

- qualification
- busy status
- trainee restriction
- cooldown
- MS requirement

then use normal candidate selection.

# 41. Render Persistence with Google Sheets

The application persists runtime data in **Google Sheets**, not on the Render filesystem.

This avoids the ephemeral-filesystem problem on Render's free web service: schedule, brothers, meetings, and settings survive redeployments and restarts because they live in Google Drive.

Requirements:

- Document Google Cloud and spreadsheet setup in the README
- Store service account credentials only in environment variables (Render secrets)
- Share the spreadsheet with the service account email (`...@....iam.gserviceaccount.com`) as Editor
- Do not rely on `storage/app/data/` for runtime persistence

The application should remain architecturally ready to migrate from:

```text
GoogleSheetsService
```

to:

```text
SQLite/Eloquent
```

or another persistent storage solution if needed later.

The scheduling algorithm must not need to change when persistence changes.

- enums where appropriate

Avoid:

- business logic in Blade
- direct Google Sheets API access from controllers
- duplicated scheduling logic
- unnecessary abstractions
- unnecessary dependencies

# 49. Scheduler Priority

When rules conflict, prioritize:

```text
1. Qualification
2. Busy/unavailable restrictions
3. Trainee restrictions
4. MS requirement
5. Cooldown
6. Required assignment
7. Weekend swap
8. Fair workload
9. Random tie-breaking
```

Never knowingly create an invalid assignment merely to satisfy fairness or swapping.

Return warnings when a valid assignment is impossible.
